# Frequently asked questions

Written to be useful when the honest answer is "this is not the right tool".
Nothing on this page is a benchmark claim; the measured numbers live in
`docs/BENCHMARKS.md` and are regenerated by `python scripts/benchmark.py`.

## What is this, in one paragraph

One shared knowledge-graph core, a schema-migrated SQLite store with full-text
search, deterministic content-derived identifiers, an append-only hash-chained
audit log, and a provenance envelope on every record, with two pluggable
analysis planes on top: a document-and-media plane and a source-code plane. It
answers questions across both and shows you the evidence for each answer. It
runs on your machine and reaches no network unless you explicitly ask it to.

## How it compares

### Against a language server

A language server understands one language properly. It resolves a name to a
definition using the compiler's own view of types, scopes, and imports, and it
is right in cases that no amount of structural analysis will get right.

This platform's default code path is structural: it matches names across a
Tree-sitter parse, so a call to `run` becomes an edge to every symbol named
`run`. That is over-approximate on purpose, and it is why every code result
carries a `why` block saying so. On the retained ambiguity corpus, structural
blast-radius scores precision 0.1081 with recall 1.0: it never missed real
impact, it reported far too much. Turning on type-aware resolution with
`dkg code-ingest --resolve`, which drives a pre-staged language server plus
local dataflow, takes the same measurement to precision 1.0 with recall 1.0.

So the honest comparison is:

| | A language server | This platform |
|---|---|---|
| Accuracy on one language | Compiler-grade | Structural by default; type-aware with `--resolve` where a server is staged |
| Languages at once | One, per server | Many, in one graph, in one query |
| Whole-repository questions | Not its job | Blast radius, execution flow, chokepoints, coupling, gaps |
| Crossing from code to documents | No | Yes, both planes write into one graph |
| Needs a running server | Yes | No, except for the optional `--resolve` path |

It does not replace a language server, and it does not try to. Where a server is
staged, it uses one.

### Against similarity retrieval

Similarity retrieval, meaning an embedding model plus a vector index, finds
passages that are semantically near a query. It is good at "find me things about
this" and bad at "show me everything that would break".

This platform has similarity retrieval in it: the optional `embeddings` extra
adds a real local embedding model and the optional `reranker` extra adds a local
cross-encoder, both pre-staged and loaded with no runtime download. What it adds
around them is structure and evidence. A vector hit is a passage; a graph answer
is a passage plus the document it came from, the claim it supports, the
confidence formula that scored it, and an audit entry recording that it was
read.

The practical difference: a vector index cannot tell you that two sources
disagree, because nearness is not disagreement. The contradiction scanner here
can, within honest limits, and it is lexical rather than an entailment model, so
its output is advisory.

If all you want is semantic search over a pile of text, a vector database is
simpler and you should use one.

### Against plain search

`grep` and `ripgrep` are extremely good, extremely fast, and have no setup cost.
For "where does this exact string appear", they win, and nothing here beats
them.

They lose when the question is not a string. "What calls this?" is not a string
query, and neither is "which components does this change reach", "where do these
two documents disagree", or "what has no test". Those need edges.

The measured picture is deliberately not a marketing one. Against a competent
grep-and-read baseline (rarity-weighted ranking, top twelve files read whole),
across four tasks, the graph route costs about twice the tokens overall, 71,088
against 34,744, and is more correct and more complete: mean correctness 1.0
against 0.6206. It wins on tokens with correctness held in two of the four
tasks, and loses on the other two. The baseline is cheap because it is
incomplete, not because it is efficient, which is why the two columns only mean
anything read together. Full detail is in `docs/BENCHMARKS.md`.

### Against a graph database

A graph database is a database. This is an application with a graph in it. If
you need a general-purpose graph store with its own query language, clustering,
and operational tooling, use one; there is an export for that
(`dkg export --format cypher`). What you would then have to build yourself is
everything above the storage: the ingestion, the extraction, the evidence
ledger, the provenance envelope, and the audit chain.

### Against a hosted service

A hosted service can be bigger than your machine and can be shared with your
team without you running anything. It also means your material leaves your
machine. This platform trades that away deliberately: it is local-first, the
network is off by default, there is no telemetry, and the core install pulls no
runtime dependency at all. If your constraint is scale rather than
confidentiality, that trade is the wrong way round for you.

## What it does not replace

Named plainly, because a tool that claims to replace everything replaces
nothing.

- **A compiler or a type checker.** It does not check your program. It does not
  know whether the code is correct.
- **A language server.** See above. It uses one when one is staged.
- **A linter or a formatter.** No style opinion, no autofix.
- **A test runner.** It can tell you which symbols look untested, from graph
  structure alone. It cannot tell you whether your tests pass.
- **A debugger or a profiler.** No runtime observation of any kind. Execution
  flow here is structural: it is what the parser saw, not what ran.
- **Version control.** It reads git history for incremental updates and for the
  optional co-change signal. It does not store or manage your history.
- **A search engine at web scale.** SQLite and FTS5 on one machine, not a
  cluster.
- **A vector database at scale.** Vectors are persisted per model in the same
  SQLite file. That is the right size for a workstation corpus and the wrong
  size for a hundred million documents.
- **A note-taking application.** There is an Obsidian vault export
  (`dkg export --format obsidian`) precisely so you can keep using yours.
- **A large language model.** No model is required, none is bundled, and the
  deterministic paths do not use one. Model adapters are optional and
  provider-neutral.
- **A vulnerability scanner.** The taint pass is advisory and
  over-approximate. `scripts/sast.py` and a dependency audit are separate
  concerns and are documented in `docs/SECURITY_MODEL.md`.

## When not to use this

- **You need certainty about impact.** The default path over-approximates by
  design, and even the resolved path is measured on a retained corpus rather
  than proven. If a wrong answer is expensive, treat every result as a prompt to
  look, not as a finding.
- **You want an answer, not evidence.** Everything here is built to be
  auditable, which makes it more verbose and slower than a tool that just
  answers.
- **Your corpus is enormous.** One SQLite file on one machine has a ceiling.
- **You need a hosted, multi-user, always-on service.** There is none, and none
  is planned. See `docs/ROADMAP.md`.
- **Your question is a string.** Use `ripgrep`.
- **You need commercial use.** The licence does not permit it. See below.
- **You need to modify the source.** The licence does not permit that either,
  nor distributing a modified version.
- **You need a language this build does not parse.** Run `dkg code-languages`
  first and see. Five languages have no installable permissive grammar and are
  read by a documented pattern fallback at reduced fidelity, which is labelled
  as such everywhere it appears.

## How to verify a working install

Six commands, in order. Each one checks something the next one depends on.

```bash
dkg --version
dkg init
dkg capabilities
dkg doctor
dkg ingest ./docs --recursive
dkg search "provenance"
```

What to expect:

1. `dkg --version` prints `dkg` and a version. If the shell cannot find `dkg`
   at all, the install did not put it on your path; see
   `docs/TROUBLESHOOTING.md`.
2. `dkg init` creates a project-local `.dkg` home with the database in it. It is
   safe to run twice.
3. `dkg capabilities` lists every optional adapter with `available` true or
   false and an honest reason for each false. A long list of false entries on a
   fresh install is correct, not broken: the core has no mandatory runtime
   dependency and every optional capability is detected rather than assumed.
4. `dkg doctor` runs the self-check and prints JSON. This is the one to paste
   into a bug report.
5. `dkg ingest ./docs --recursive` ingests this repository's own documentation,
   which is a corpus you already have. It should report a document count above
   zero.
6. `dkg search "provenance"` should return hits from what you just ingested. If
   ingestion reported documents and search returns nothing, that is a real
   problem and worth reporting.

Then two more, if you want to check the read-only surfaces:

```bash
dkg audit --verify
dkg export --format json --out /tmp/graph.json
```

`dkg audit --verify` walks the append-only hash chain and tells you whether it
is intact. `dkg export` writes the graph out; if that works, the store is
readable end to end.

For the environment rather than the install, run the diagnostic:

```bash
python scripts/probe_environment.py
```

It prints one JSON document naming the interpreter, which optional extras are
installed, which external binaries and pre-staged models it found, whether this
shell can bind a loopback port, and whether the package index is reachable. That
last check is the only outbound request the script can make, it names the URL it
contacts in its own output, and `--offline` skips it. The pairing is the point:
"the install failed" and "this shell cannot reach anything" look identical from
the inside until you see both answers together.

### It installed but the code plane does nothing

That is expected until you install a code extra. Parsing is optional:

```bash
pip install -e ".[code]"          # Python, JavaScript, Go
pip install -e ".[code-extended]" # plus TypeScript, TSX, Java, Ruby, Rust
pip install -e ".[code-full]"     # the full grammar set
dkg code-languages                # what this build can actually parse
```

`dkg code-languages` is the authority. A language whose grammar is absent is
reported as unavailable rather than silently returning nothing.

## Privacy and network

### Does it phone home?

No. There is no telemetry to disable. Outbound network is off by default; the
web and feed readers require an explicit `--allow-network` flag and a
configuration allowance, and every fetch passes a post-resolution address check
that rejects private, loopback, link-local, multicast, reserved, and
cloud-metadata addresses.

### Does it download models?

Never at runtime. The embedding, reranker, and detection models are pre-staged
by `scripts/prestage_models.py`, which is a build-time tool, and are then loaded
local-files-only. If a model is not staged, the capability reports itself
unavailable with a reason and the system degrades to the documented fallback.

### Can I run it fully air-gapped?

Yes, and that is the default posture. The one place the project reaches the
network on purpose is build and continuous-integration tooling, plus the
disclosed reachability probe in the diagnostic script.

## Evidence and status

### How do I know a capability actually works?

`docs/REQUIREMENTS_TRACEABILITY_MATRIX.csv` is the status source of truth,
validated by `scripts/validate_traceability.py` and mirrored into
`docs/traceability_summary.json`. A row is production ready only when its
implementation files resolve on disk, its acceptance is an executed test that
passes, and its evidence is a real run rather than a manual note. Rows that do
not meet that bar say so.

### Why do so many results carry a caveat?

Because they are over-approximate and the alternative would be to hide it. The
underlying code edges are structural, community indices are arbitrary labels
produced independently per run, and review questions are worded as questions
because they are prompts for a person rather than findings.
